Protocol

ATTEST in one page

ATTEST is a settlement and attestation layer for machine services. A payer agent sends USDC through x402 into a per-call escrow. The provider signs the exact delivery it produced. A verifier compares that delivery with the spec committed before work started and then settles or slashes. The outcome is a public receipt account.

Why escrow at all

x402 proves that a payment was authorized. It does not prove that the service was delivered. Without a delivery commitment, an agent either has to trust the provider or run an unsecured prepayment. ATTEST makes the obligation explicit: the escrow amount, the spec hash, the provider, the payer and the deadline are fixed before any work. The provider bonds USDC, so a wrong delivery has a cost.

Lifecycle

  • Quote. The API derives an escrow address from the agent wallet, the provider and a nonce derived from the idempotency key. It returns an x402 challenge whose payTo is the escrow vault.
  • Payment. The agent signs an exact-SVM payment. The API verifies it with the facilitator, checks the payer matches the registered wallet, settles it, and only then opens the escrow.
  • Delivery. The provider produces the report, hashes the canonical delivery payload, signs attest:v1 || escrow || spec_hash || delivery_hash || deadline and submits it with the Ed25519 precompile.
  • Verdict. Valid delivery releases the escrow to the provider. Invalid delivery returns the amount to the payer and charges the bond. Missing delivery can be slashed permissionlessly after the deadline.

HTTP API

POST /v1/quotes            x-api-key, idempotency-key -> { quote, paymentRequired }
POST /v1/reports/:quoteId  payment-signature -> { receipt, replayed, verification? }
GET  /v1/budget            x-api-key -> BudgetDto
GET  /v1/receipts          public list
GET  /v1/receipts/:id      public receipt
GET  /v1/stats             public aggregates
GET  /v1/providers         public bond/exposure list
GET  /health               liveness, network, provider bond

A 402 response carries the x402 challenge in both the JSON body and the PAYMENT-REQUIRED header. A successful payment echoes PAYMENT-RESPONSE.

SDK

import { createClient } from "@attest/sdk";

const client = createClient({
  apiBaseUrl: "http://127.0.0.1:4021",
  apiKey: process.env.ATTEST_API_KEY,
  rpcUrl: "https://api.devnet.solana.com",
  signer, // a @solana/kit TransactionSigner
});

const { receipt } = await client.pay({ topic: "Settlement risk" });
const verification = await client.verifyReceipt(receipt.id);
const budget = await client.getBudget();

MCP

The MCP server exposes four tools: attest_pay, attest_verify_receipt, attest_budget and attest_receipts. Configure it with ATTEST_API_URL, ATTEST_API_KEY, ATTEST_RPC_URL and ATTEST_SIGNER_KEYPAIR.

{
  "mcpServers": {
    "attest": {
      "command": "node",
      "args": ["packages/mcp/dist/cli.js"],
      "env": {
        "ATTEST_API_URL": "http://127.0.0.1:4021",
        "ATTEST_SIGNER_KEYPAIR": "/absolute/path/to/agent.json"
      }
    }
  }
}

Safety model

  • Budgets are checked and charged server-side; a settled payment cannot overspend.
  • Payments are deduplicated by the first signature in the signed transaction.
  • The payer must match the agent's registered wallet before settlement.
  • The provider bond penalty is min(escrow amount, staked, vault balance), so a slash is always funded.
  • Every transaction is v1, and every transaction read caps maxSupportedTransactionVersion at 1.

Local setup

See the repository README for exact commands. Devnet needs SOL for fees and devnet USDC for the provider bond and the payer. The seed script never prints private keys.
